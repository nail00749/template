# gvozdla: руководство для пользователей

Команды соответствуют версии **0.1.0**. gvozdla создаёт проект из Git-шаблона,
сохраняет его исходную базу и переносит обновления выбранных частей шаблона.
Сейчас доступен шаблон `tanstack` и дополнительная возможность `keycloak-auth`.

## Установка и обновление CLI

Нужны Git, Bun >= 1.2 и npm для этой команды установки:

```bash
npm install -g gvozdla
gvozdla --version
gvozdla --help
```

Для обновления самой утилиты повтори `npm install -g gvozdla@latest`.
`gvozdla update` обновляет проект из шаблона, а не установленную CLI.

Bun должен быть доступен в `PATH`: именно он запускает CLI. Сам TanStack-шаблон
сейчас задаёт Bun 1.4.3 в `packageManager` своего `package.json`.
Зависимости проекта и необходимый backend устанавливаются/настраиваются отдельно.

## Первый проект

Из каталога, в котором будет лежать новый проект:

```bash
gvozdla create ./my-app --template tanstack --no-install --init-git
cd my-app
bun install
git add .
git commit -m "[NO-TICKET] initialize project from template"
```

Каталог `my-app` должен отсутствовать. `--init-git` создаёт новый репозиторий,
но не делает первый коммит. В коммит должна попасть вся `.template/`.

В обычном терминале CLI предлагает выбрать features. Стрелки перемещают курсор,
Space меняет выбор, Enter подтверждает. Для установки зависимостей сразу можно
передать `--install`; установка может запускать lifecycle scripts пакетов.

Чтобы запустить приложение после установки, создай в корне проекта `.env` с
адресами своего фронтенда и backend, например:

```dotenv
SERVER_URL=http://localhost:3000
VITE_API_BASE_URL=http://localhost:8002
```

Затем выполни `bun run dev`. Backend по этому адресу должен поддерживать API
шаблона, включая проверку сессии. gvozdla не разворачивает backend и Keycloak;
успешная генерация проекта не проверяет доступность этих сервисов.

### С авторизацией Keycloak

```bash
gvozdla create ./my-app \
  --template tanstack \
  --feature keycloak-auth \
  --no-install \
  --init-git
```

Feature добавляет интеграцию с backend-owned OIDC flow. Требования к backend
описаны в созданном проекте в `.docs/auth.md`.

### Что выбрать в автоматическом запуске

Без TTY каталог обязателен; установка зависимостей и Git по умолчанию выключены,
а features без `--feature` не выбираются. Для скрипта укажи нужные флаги явно:

```bash
gvozdla create ./my-app \
  --template tanstack \
  --feature keycloak-auth \
  --no-install \
  --init-git
```

## Какие файлы сопровождает шаблон

Группы определяются `template.manifest.json` в исходном репозитории. Текущий
TanStack-шаблон сопровождает:

| Группа    | Содержимое                                                                         |
| --------- | ---------------------------------------------------------------------------------- |
| `ui`      | `src/shared/ui/**`; требует также группу `utils`                                   |
| `utils`   | `src/shared/lib/**`                                                                |
| `tooling` | `.oxlintrc.json`, `.oxfmtrc.json`, `.oxfmtignore`, `scripts/check-architecture.ts` |

Страницы приложения, конфигурация окружения, API-клиенты, зависимости в
`package.json` и package-manager lock-файлы автоматически не обновляются.
Файлы вне сопровождаемых групп выдаются при создании и остаются кодом проекта.
Не вся папка `shared` является общей частью шаблона.

Проект хранит:

```text
.template/project.json   источник, tracking ref и выбранные features
.template/lock.json      принятые SHA групп и записи сопровождаемых файлов
.template/objects/       исходные байты файлов, адресуемые по SHA-256
.template.json          старые метаданные совместимости
```

Храни всю `.template/` в Git. Не редактируй базу и lock вручную: это не способ
разрешения конфликтов или отметки обновления как принятого. Одной старой
`.template.json` недостаточно для `status` и `update`.

## Посмотреть состояние

Следующие команды выполняются **из корня созданного проекта**:

```bash
gvozdla status
gvozdla status --remote
```

Первая команда работает без сети: показывает принятые SHA групп и изменения/
удаления файлов относительно базы. Новые проектные файлы без базы она не
перечисляет. Наличие локальных изменений само по себе не означает ошибку.

`--remote` получает текущий tracking ref и показывает план обновления с возможными
конфликтами. Он не применяет изменения. Для вызова из другого каталога передай
`--project /path/to/my-app`.

## Обновить проект

Сначала проверь, что Git-репозиторий находится именно в корне проекта и имеет
первый коммит. Незакоммиченные изменения нужно самостоятельно сохранить или
разобрать до применения обновления; просмотр плана доступен и до этого.

```bash
git status --short
gvozdla update --only ui,tooling --dry-run
```

Для `ui` CLI добавит зависимость `utils`. Если план подходит и конфликтов нет:

```bash
gvozdla update --only ui,tooling
git status --short
git diff --stat
git diff
bun run check
bun run typecheck
bun run test
bun run build
```

CLI создаёт ветку `feat/gvozdla-update-*` и оставляет изменения незакоммиченными.
Если обновлять нечего, новая ветка не создаётся.
После проверки результата закоммить выбранные изменения проекта и `.template/`,
а затем оформи PR обычным способом. CLI не создаёт этот коммит и PR автоматически.
Для обновления всех сопровождаемых групп опусти `--only`.

Объединение учитывает старый шаблон, код проекта и новый шаблон. Независимые
проектные правки сохраняются. База обновляется до новой версии шаблона, поэтому
дальнейшие обновления продолжают отличать кастомизацию от исходного кода.
Изменение только SHA/метаданных тоже может потребовать коммита без изменения UI-файлов.

`update` не запускает проверки проекта, не устанавливает зависимости и не
выполняет скачанные hooks. Успешное текстовое объединение не гарантирует
совместимость: новый компонент может потребовать ручного изменения зависимостей.

### Другой источник или версия шаблона

При создании можно задать другой Git-репозиторий с совместимым манифестом:

```bash
gvozdla create ./my-app --repo /path/to/template-repo --ref main --no-install --init-git
```

Локальный источник должен содержать закоммиченные изменения: CLI клонирует Git,
а не текущую рабочую папку. Поддерживаются существующие имена веток и тегов;
произвольный commit SHA для `--ref` в этом MVP не поддерживается.

Чтобы попробовать другую существующую ветку/тег уже подключённого источника,
передай `--ref` в `update --dry-run` или `status --remote`. Для применения
повтори `update` с тем же `--ref`. Этот флаг действует только на одну операцию
и не меняет сохранённый tracking ref. Например, переход с `main` на тег сам по
себе не закрепляет дальнейшие обновления на этом теге.

## Если найдены конфликты

CLI перечисляет пути и причины, возвращает код 2 и не применяет выбранное
обновление целиком: файлы, ветка и база проекта остаются прежними.
Это относится и к удалению изменённого файла, совпадению пути нового файла с
проектным, и несовместимым изменениям двоичных файлов.

Можно обновить другие группы, не затронутые конфликтом, явно выбрав их через
`--only`. Учитывай автоматическое включение зависимостей: запрос `ui` всё равно
включает `utils`.

Если ты вручную приводишь конфликтующий файл к нужной версии источника,
сохрани исправление в Git и заново посмотри план. Простое повторение команды
с неизменёнными конфликтующими версиями проблему не решит. Для сохранения
несовместимой кастомизации отложи эту группу: выбора «оставить своё и принять
новую базу» пока нет. Не исправляй это редактированием `.template/lock.json`.

Флагов `--force`, `--continue`, `--abort`, а также интерактивного выбора hunks
в версии 0.1.0 нет. Если ошибка прервала применение, изучи `git status` и
`git diff`: CLI пытается откатить свои записи, но не гарантирует восстановление
после завершения процесса/сбоя питания. Сохраняй посторонние изменения.
Переключение ветки само по себе не отменяет незакоммиченный diff.

## Частые ошибки и ограничения

| Ситуация                              | Что делать                                                                                                     |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `bun` или `gvozdla` не найден         | Проверить установку и `PATH`, открыть новый терминал                                                           |
| Каталог назначения существует         | Выбрать новый отсутствующий каталог; CLI не дописывает проект поверх существующего                             |
| Нет `.template/project.json`          | Проверить каталог; старый scaffold и скопированные проекты автоматически не подключаются                       |
| Требуется clean Git working tree      | Изучить `git status`, сохранить свои изменения и первый коммит                                                 |
| Найден родительский Git-репозиторий   | Созданному проекту нужен собственный Git-корень                                                                |
| Повреждён/отсутствует baseline object | Восстановить соответствующую `.template/` из известного корректного коммита; не подставлять новые хеши вручную |
| Требуется migration                   | Изменение владения файлами/политик групп не поддерживается автоматически                                       |

`contribute`, `adopt`, `templates list`, автоматическая отправка PR/MR и миграции
ещё не реализованы. Добавлять features после генерации и обновлять отдельные
JSON-ключи `package.json` текущая версия тоже не умеет.

Для скриптов и AI-агентов см. [отдельные инструкции](gvozdla-agents.md).
Устройство манифеста и базы описано в [архитектуре](gvozdla-architecture.md).
