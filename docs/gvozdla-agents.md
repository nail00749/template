# gvozdla: инструкции для AI-агентов и автоматизации

Применяется к **gvozdla 0.1.0**. Это инструкция по использованию установленной
утилиты в проекте. Учитывай инструкции пользователя и `AGENTS.md` конкретного
репозитория; этот файл не заменяет их и не даёт дополнительных разрешений на
публикацию, merge или работу с чужими проектами.

## Определить состояние до изменений

1. Прочитай инструкции проекта, уточни его каталог и границы запрошенной работы.
2. Проверь `gvozdla --version` и `gvozdla --help`.
3. Для существующего проекта прочитай `.template/project.json` и `lock.json`,
   проверь `git status --short` и `git rev-parse --show-toplevel` из его корня.
4. Начни с `gvozdla status --json`. Он работает офлайн и не проверяет доступные
   обновления источника. Его `changes` содержит только файлы с сохранённой базой.

Нет `.template/` — это не управляемый проект для текущего CLI. Нельзя синтезировать
базу из текущего `shared`, считать последнюю `main` исходной версией или заменять
отсутствующую базу одной `.template.json`. Команда `adopt` пока не существует.

## Создать новый проект без вопросов терминала

Выполняй из родительского каталога. Назначение должно отсутствовать:

```bash
gvozdla create ./my-app \
  --template tanstack \
  --feature keycloak-auth \
  --no-install \
  --init-git
```

`--feature keycloak-auth` добавляй, только когда это нужно задаче. Если features
не нужны, опусти флаг. Без TTY features не выбираются автоматически. В терминале
создание может открыть интерактивный выбор; для автоматизации запускай процесс
без TTY, указывая каталог и положительные/отрицательные install/Git-флаги явно.
Флага `--yes` у CLI нет. `--json` у `create` тоже нет.

`--init-git` не создаёт первый коммит. Установка зависимостей и запуск приложения
— отдельные шаги. Прочитай `packageManager`, scripts и документацию окружения
созданного проекта. Для текущего TanStack-шаблона нужны Bun 1.4.3 и backend API;
выбранный feature не разворачивает backend или Keycloak.

Перед первым обновлением проект должен иметь собственный Git-корень и коммит
с созданными файлами и всей `.template/`. Создавай коммиты в рамках поручения;
не переписывай постороннюю историю ради выполнения предусловия.

## Сначала получить план, затем применить

Следующие команды выполняются из корня управляемого проекта:

```bash
gvozdla status --json
gvozdla update --only ui,tooling --dry-run --json
```

Из другого каталога добавляй `--project /absolute/path/to/project`.
Нужные группы определяются задачей и манифестом. `ui` включает зависимость
`utils`; не обещай обновить только один физический каталог. Без `--only`
обновляются все сопровождаемые группы. `status --remote --json` получает
план для всех групп, но ничего не применяет.

При необходимости передай существующую ветку/тег через `--ref` в просмотр
и в применение. Источник берётся из сохранённого config, а `--ref` не меняет
его tracking ref. Commit SHA не поддерживается текущим Git checkout CLI.

Выполняй применение, когда оно входит в поручение пользователя, план подходит,
конфликтов нет, а Git-дерево чистое:

```bash
gvozdla update --only ui,tooling --json
git status --short
git diff --stat
git diff
```

Не добавляй новую точку согласования, если пользователь уже разрешил обновление.
Если задача была только посмотреть доступные изменения, остановись на плане.
Не делай автоматический stash, reset, clean или удаление чужих изменений ради
clean tree. Не сохраняй JSON-план/логи внутри проекта перед применением: новый
незакоммиченный файл тоже делает дерево грязным. Используй stdout или временный
каталог вне проекта.

## Контракт JSON и коды завершения

| Код | Значение               | Действие агента                                                                        |
| --- | ---------------------- | -------------------------------------------------------------------------------------- |
| `0` | Команда выполнена      | Изучить данные; это не означает отсутствие обновлений или успешные проверки приложения |
| `1` | Ошибка                 | Прочитать stderr; stdout может не содержать JSON                                       |
| `2` | В плане есть конфликты | Не применять; сообщить пути/причины и отложенные группы                                |

Код 2 возможен у `status --remote`, `update --dry-run` и обычного `update`.
Не считай ненулевой код «обновлений нет». В shell с `set -e` перехватывай код
через `if`, прежде чем разбирать результат. Например, план можно посмотреть так:

```sh
if gvozdla update --only ui --dry-run --json; then
  printf '%s\n' 'План получен; проверь changed, actions и conflicts.'
else
  gvozdla_exit=$?
  case "$gvozdla_exit" in
    2) printf '%s\n' 'Есть конфликты; обновление не применено.' ;;
    *) printf '%s\n' 'Ошибка команды; смотри stderr.' >&2 ;;
  esac
  exit "$gvozdla_exit"
fi
```

Офлайн-статус содержит `templateId`, `source`, `groups`, `changes`. Группы имеют
принятый `revision`, число `files`, `modified` и `deleted`. Локальные изменения
относительно базы могут быть уже закоммичены: этот статус не заменяет Git status.

План содержит `templateId`, целевой `revision`, фактические `groups`, `actions`,
`conflicts` и `changed`. Действия имеют `path`, `group`, `kind`:
`add`, `update`, `delete` или `keep`. Конфликт содержит `path`, `group`, `reason`.
Все пути относятся к корню созданного проекта. JSON не содержит самих baseline
байтов. Не обещай суммарный номер версии проекта: у групп могут быть разные SHA.

Результат применения дополнительно содержит `branch` и `applied: true`.
`branch: null` допустим для no-op; один только `applied: true` не доказывает
изменение файлов. `changed` может быть true из-за продвижения метаданных базы,
даже если все файловые действия имеют `kind: "keep"`.

## Проверить и передать результат

Успешное применение оставляет diff в новой ветке `feat/gvozdla-update-*`.
CLI не запускает проверки, установку зависимостей, коммит или отправку PR.
Запусти проверки, предписанные проектом. Для текущего TanStack-шаблона:

```bash
bun run check
bun run typecheck
bun run test
bun run build
```

Проверь изменённые файлы и `.template/` вместе. Не выдавай автоматическое
объединение текста за доказательство корректной работы приложения. Если компоненту
нужна новая зависимость, учитывай её отдельно: dependency manifests и lock-файлы
в текущем манифесте gvozdla не сопровождаются.

В отчёте укажи выбранные и реально включённые группы, принятый SHA, созданную
ветку/отсутствие изменений, проверки и оставшиеся конфликты. Коммит, PR, merge
и публикацию выполняй только в рамках разрешённого объёма работы. Уже полученное
разрешение не нужно запрашивать повторно.

## Конфликты, ошибки и ограничения

При конфликте CLI блокирует выбранное обновление целиком; состояние проекта
и база не продвигаются. Можно предложить обновление других независимых групп,
учитывая их зависимости. Не повторяй один и тот же конфликтующий запуск без
изменения ситуации и не подменяй конфликт успешным статусом в автоматизации.

Принятия новой базы с сохранением конфликтующей локальной версии в 0.1.0 нет.
Если нужен именно такой результат, явно опиши ограничение и отложи группу.
Флагов `--force`, `--continue`, `--abort`, команд `diff`, `contribute`, `adopt`,
`templates list`, индивидуального skip файла и интерактивного merge нет.

При ошибке записи CLI пытается откатить собственные изменения. После аварийного
завершения изучи Git-состояние: транзакционный журнал и гарантия восстановления
после сбоя питания отсутствуют. Не выполняй общий reset/clean для восстановления.
Не меняй `.template/lock.json`, objects или config вручную, чтобы обойти валидацию.

Обновление исходников самого шаблона — отдельная задача. CLI пока не умеет
отправлять проектные исправления обратно автоматически. Не редактируй файлы
глобально установленного npm-пакета для изменения исходного Git-шаблона.

## Как подключить эту инструкцию к агенту проекта

Добавь в существующий `AGENTS.md` проекта ссылку на этот документ и команду
проверки установленной версии, не заменяя остальные инструкции. В репозитории
шаблона документ находится в `docs/gvozdla-agents.md`; в следующих npm-релизах
он также будет доступен в `$(npm root -g)/gvozdla/docs/gvozdla-agents.md`.
Архив npm 0.1.0, опубликованный до этого документа, новых guide-файлов не содержит.

После слияния документации можно вставить в `AGENTS.md` такой блок:

```markdown
## Обновления шаблона через gvozdla

Перед работой прочитай https://github.com/nail00749/template/blob/main/docs/gvozdla-agents.md
и проверь `gvozdla --version`. Сначала получи план `update --dry-run --json`.
Не изменяй `.template/` вручную и сохраняй посторонние изменения проекта.
Учитывай инструкции пользователя и этого репозитория.
```

Практические примеры и восстановление: [руководство пользователя](gvozdla-guide.md).
Манифест, база и правила объединения: [архитектура](gvozdla-architecture.md).
